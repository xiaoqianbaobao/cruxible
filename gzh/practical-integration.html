01

Natural Language Ontology

让业务人员用自然语言定义领域模型

之前建本体只有一条路：写 YAML → PR → 上线。每改一个字段都要走一遍。我们在 Cruxible 里加了 6 个增量操作工具，把这条路改成了对话式的：

场景：业务说"我们要管项目下的阶段"

STEP 1 Agent 先看当前本体

→ cruxible_ontology_describe(instance_id=...)

返回：Entity types: Project, Task, Actor, Decision, Risk / Relationships: 5 / Enums: 4

STEP 2 Agent 新增实体

→ cruxible_entity_type_add(instance_id, name="Stage",

　　properties={"name": {"type": "string"},

　　"deadline": {"type": "date", "optional": true}},

　　dry_run=True)

STEP 3 Agent 新增关系

→ cruxible_relationship_add(instance_id,

　　name="stage_belongs_to_project",

　　from_entity="Stage", to_entity="Project",

　　dry_run=True)

STEP 4 业务确认，apply 生效

→ cruxible_entity_type_add(name="Stage", ..., dry_run=False)

→ cruxible_relationship_add(name="stage_belongs_to_project", ..., dry_run=False)

引擎自动校验约束 → 写入知识图谱 → 生成 receipt → 业务可见

「整个过程中，业务人员没有写一行 YAML，没有提一个 PR。Agent 负责翻译自然语言，Cruxible 负责校验和执行。」


02

Schema Discovery

从大数据到本体：一键扫描现有数据源

大部分团队已经有数据——Hive 表、OceanBase 库、SFTP 上的 CSV 文件。从头建本体不如从现有数据反推。我们加了三个连接器：

1

Hive/Spark——连接 Hive Metastore，SHOW TABLES → DESCRIBE → 自动推断实体类型、属性、FK 关系。ODS/DWD/DIM 前缀自动剥离。

2

OceanBase——同 MySQL 协议，扫描 INFORMATION_SCHEMA，检测主键和外键约束，自动生成 relationship 提案。

3

SFTP 文件——远程 CSV/JSON 采样 → 推断列类型和枚举值 → 推荐实体结构。

调用只有一个工具：

→ cruxible_discover_schema(source_type="hive",

　　host="hive-server", port=10000,

　　database="default")

返回结果包含发现的实体类型、属性、关系提案——这些提案不会自动写入，而是交给人或 Agent 审核后，再用上一节的新增工具逐步应用。自底向上（数据→本体）和自顶向下（对话→本体）两条路径都打通了。


03

MCP Integration

与超级智能体底座的 MCP 集成

Cruxible 的 81 个工具全部注册为 MCP（Model Context Protocol）服务。任何支持 MCP 的 Agent 底座——包括开源项目 DeerFlow——都可以直接使用这些工具。

集成只需要两步

STEP 1 启动 Cruxible Daemon

$ cruxible server start --port 8100

Daemon 在 :8100 监听 HTTP REST API，管理所有实例和持久化。

STEP 2 在 Agent 底座配置 MCP Server

# extensions_config.json

{"mcpServers": {

　"cruxible": {

　　"command": "python3 -m cruxible_core.mcp.server",

　　"env": {"CRUXIBLE_SERVER_URL": "http://host:8100"}

　}}}

Agent 底座自动发现 81 个工具，Agent 在规划时就能看到全部工具清单。

对于 Docker 部署的底座（如 DeerFlow），只需在容器内安装 cruxible-core 并将 CRUXIBLE_SERVER_URL 指向宿主机的 daemon。Agent 通过 MCP stdio 管道与 Cruxible 通信——不是 HTTP，而是标准输入输出，零网络开销。

Roadmap

后续规划

81 个工具、3 个数据源连接器、6 个本体编辑工具——这是当前的状态。后续计划分三阶段：

1

生产化部署——daemon 稳定性、CRUXIBLE_MODE 权限分级、Agent 工具调用监控

2

治理反馈闭环——完整的 propose → evaluate → feedback → resolve 链路，让每个 Agent 写图的动作都经过确定性检查和人工兜底

3

规模化扩展——NebulaGraph 后端集成、跨实例联邦查询、连接器插件化

81 个工具，只是起点。
当 Agent 能自己发现本体、编辑本体、并经过治理写入知识图谱时，
我们才真正解决了 Agent 的"失忆症"。
