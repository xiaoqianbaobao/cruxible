01

Ontology

从哲学概念到工程工具

本体论原本是哲学的一个分支，研究"存在"的分类。在信息科学中，它被 Tom Gruber 在 1993 年简化为一个极其实用的定义：

「本体论是对某一领域共享概念的形式化、显式的规格说明。」

翻译成工程语言就是： 用机器可读的方式告诉系统你的世界里有什么东西，它们之间怎么关联，以及这些关联必须遵守什么规则。

一个电商领域的本体论告诉你：有 User 、 Product 、 Order 三种实体；User 可以下（places）一个 Order；Order 包含若干 Product；一个有效的 Order 必须至少包含一个 Product。

但传统的本体论实现——OWL、RDF——太学术化了。它们缺乏构建时校验、运行时快照、变更审计这些工程层的能力。而 LLM 时代的本体论需要回答一个更实际的问题：

CORE QUESTION

AI Agent 如何在不写 SQL、不操作 ORM、不画 ER 图的前提下，可靠地读写结构化的领域知识？


02

Architecture

两个系统，各司其职

在回答"怎么做"之前，先看两个工具各自扮演的角色。

DeerFlow（quickFlow）：Agent 的执行侧

DeerFlow 是一个开源的 Super Agent 框架，提供了 子 Agent 协调、Sandbox 隔离、Skill 管理、MCP 集成、多租户 等能力。简单说，它负责 Agent 怎么想——推理、工具调用、子任务分解。

但它不负责 Agent 怎么记。DeerFlow 本身没有结构化的长期状态层。Agent 在对话中产生的决策、关系、推理链，随着会话结束就消失了——这是一个在生产环境亟待解决的问题。

Cruxible：Agent 的确定性状态引擎

Cruxible 正好补上这一层。它的核心设计是 四个原语 ：Config（用 YAML 声明领域本体）、Ingest（按本体定义映射入图）、Query（带图遍历的结构化查询）、Feedback（反馈审计与治理链路）。

关键设计决策： Cruxible 没有 LLM 依赖。 它是纯粹的确定性运行时。LLM 通过 MCP 工具调用它，但它的执行不涉及任何概率推理。每一步操作都产生可验证的收据（Receipt）。

MCP 作为粘合剂

DeerFlow 原生支持 MCP（Model Context Protocol）。Cruxible 的 74 个工具全部注册为 MCP 服务。集成架构极简，却极其有效：

ARCHITECTURE

DeerFlow Agent ↔ MCP stdio（74 tools）↔ Cruxible MCP Server ↔ HTTP API ↔ Cruxible Daemon（SQLite | NetworkX Graph）

DeerFlow 的 MultiServerMCPClient 自动发现 MCP 工具列表，Agent 在规划时就能看到 cruxible_init 、 cruxible_add_entity 、 cruxible_query 等全部工具，无需额外配置。MCP 协议在这里不仅是"工具调用"，它成了 Agent 平台与确定性状态层之间的标准化通道。


03

Ontology In Code

用 YAML 定义领域知识

理论讲完了，看代码。下面是一个真实可运行的项目管理本体——它定义了小型 Scrum 团队的领域模型，包括 5 种实体、5 种关系和 4 组枚举词汇：

. . . yaml

enums:

　priority: {values: [low, medium, high, critical], ordered: low_to_high}

　work_status: [backlog, planned, in_progress, blocked, review, done]

entity_types:

　Project:

　　id: project_id

　　properties:

　　　name: {type: string, indexed: true}

　　　priority: {type: string, enum_ref: priority}

　Task:

　　id: task_id

　　properties:

　　　title: {type: string, indexed: true}

　　　status: {type: string, enum_ref: work_status}

relationships:

　- task_belongs_to_project: Task -> Project

　- task_assigned_to_actor: Task -> Actor

　- task_depends_on_task: Task -> Task

　　proposal_policy:

　　　signals:

　　　　source_evidence: {role: required}

这段不到 40 行的 YAML 定义了一个完整的领域本体，包含四个层次：

1

词汇层——enums 声明共享词汇，Agent 写入时自动校验

2

实体层——定义了 5 种实体各自的属性、类型、主键、索引

3

关系层——定义了实体间的连接方式、方向与基数

4

治理层——proposal_policy 声明某些关系只能通过提案-审批流进入

三层本体结构

在真实部署中，本体不是一块铁板。Cruxible 的 Kit 机制支持分层组合——企业可以维护基础层（业务核心实体）、操作层（Agent 运营实体）、应用层（继承前两层的基础上添加特有实体），通过 extends 声明继承关系，得到一个统一的、可查询的本体视图。

约束层——让本体"活"起来

仅有实体和关系，本体论不完整。真正的业务逻辑体现在 约束 中。Cruxible 的 constraints 块定义了跨实体的业务规则：

. . . yaml

constraints:

　- name: no_self_dependency

　　rule: "depends_on.FROM.task_id != depends_on.TO.task_id"

　　severity: error

　- name: critical_task_needs_assignee

　　rule: "Task.priority == 'critical' IMPLIES Task.assigned_to IS NOT EMPTY"

　　severity: warning

这些约束在 cruxible_evaluate 时被引擎系统化检查。Agent 只需要一次调用就能发现图中的所有一致性违反，无需自己编写规则逻辑。这也是"确定性执行"的关键含义—— 校验责任在引擎，不在 LLM。


04

Hands-On

完整链路：Agent 自主操作本体

集成完成后，DeerFlow 中的 Agent 可以这样与 Cruxible 交互——每个步骤由 Agent 自主规划并执行。因为工具是确定性的，每一步都产生可审计的 Receipt：

CASE 01 校验配置

Agent 调用 cruxible_validate(config_yaml=...) 校验本体 YAML。返回 entity_types = [Actor, Project, Task, Decision, Risk]、relationships = [...]，五个实体类型和五个关系全部通过校验。

CASE 02 初始化实例

Agent 调用 cruxible_init(root_dir=..., config_yaml=...) 创建实例。返回 instance_id，图引擎 + SQLite 存储后端就绪。

CASE 03 写入实体与关系

Agent 依次写入 5 个实体（1 个项目、2 个角色、2 个任务、1 个决策）和 6 条关系（归属、指派、依赖、决策影响）。每次写入返回收据 ID。

CASE 04 查询与评估

cruxible_stats 返回 entity_count=5, edge_count=6。cruxible_evaluate 发现 7 条 finding，包括孤儿实体（Actor 无指派关系）、覆盖缺口（Decision 类型定义了但图中暂无实例）等。

「整个过程由 Agent 自主规划并执行，每一步都产生可审计的 Receipt。约束检查由引擎执行，不依赖 LLM 的诚实度。」

Epilogue

写在最后

本体论不是一个新概念。它在知识工程时代的失败，不是因为理论错了，而是因为当时的工具需要 人类手动维护 ——写 OWL 文件的成本和收益永远不成正比。

LLM + 确定性引擎的组合改变了这个等式：

LLM

负责理解自然语言，把非结构化的需求映射到本体结构上

Engine

负责执行、验证、审计，保证状态的一致性和可靠性

两个系统各司其职，不越界。DeerFlow 与 Cruxible 的 MCP 集成是这个模式的一个具体实现。它展示了 Agent 如何在不需要理解 SQL、不需要配置 ORM、不需要画 ER 图的前提下， 可靠地管理结构化的长期状态 。

当你下次部署 Agent 时，值得问自己一个问题：
你的 Agent 记得它五分钟前做过什么吗？
